  各层详细分析

  L1 领域层 (85%) — 基本完整

  已实现:
  - State: 不可变、缓存hashCode、applyJointAction 支持同步联合动作
  - Action: 37个预分配静态实例（4 Move + 16 Push + 16 Pull + 1 NoOp）
  - Level: 预计算 boxGoalsByType、allBoxGoalPositions、agentGoalPositionMap
  - Position: flyweight缓存（Position.initCache）
  - 颜色约束在 Level.canAgentMoveBox() 中强制执行

  缺失/问题:
  - applyJointAction 仅防御越界，其他不适用动作静默通过（注释声明"legacy stuck-recovery"需要）

  L2 单Agent求解层 (55%) — IW(1)严重利用不足

  已实现:
  - BoxSearchPlanner: 加权A* + TrueDistance/Manhattan启发式
  - IW1Planner: novelty=1 BFS，用于escape子目标
  - TrueDistanceHeuristic: BFS预计算距离

  关键缺失:
  - FF-style (delete-relaxation) 启发式 — claudeopus47明确推荐但未实现
  - SIW (Serialized Iterated Width) — 文档中提及但未实现
  - IW(1)通用化: 代码中定义了 IW1_FINDROUTE_MIN_MANHATTAN=10 和 MAX=35 常量，暗示应该用于一般find-route场景，但实际上
  planSubgoal() 只对escape子目标调用IW(1)，其他子目标从未触发

  L3 任务分解层 (65%) — 核心强但缺少深度

  已实现（较强）:
  - 可达性依赖分析（computeGoalDependencies）：假设阻塞法检测硬依赖 + agent-body依赖 + start-to-goal依赖
  - Hungarian最优box-goal分配
  - EscapeSubgoalSynthesizer: 合成P_temp逃脱子目标打破2-cycle
  - BlockerReliefSynthesizer: NAMO跨色辅助子目标
  - P4冲突驱动PP: 失败后提升blocker目标优先级
  - 5层tie-breaking排序（重要性→冲突→窄路→任务数→距离）

  缺失:
  - 递归HTN分解: 当前是扁平的subgoal列表，不是递归的"大任务→子任务→原子动作"
  - Subgoal级约束分裂（CBS-lite）: P4只是重排序，没有真正的"在subgoal A和B之间生成约束 → 两个分支各自求解"

  L4 协调层 (50%) — 只有PP一种实现

  已实现:
  - PP中的多层冲突处理: ConflictResolver → ConflictDetector → AgentCoordinator(yielding/clearing) → DeadlockBreaker
  - CrossColorBarrierAnalyzer: 跨色障碍检测
  - ReservationTable: 时空预约表

  关键缺失:
  - 完整CBS算法 — 有意排除（CLAUDE.md声明"CBS/JointAStar removed from top-level
  sequences"），但claudeopus47建议的CBS-lite也未完整实现
  - Action级约束分支: CBS精神的"碰撞→生成约束→分支重规划"仅在subgoal排序层面存在，未在action层面实现
  - 所有portfolio策略都是PP变体（不同排序模式），没有真正异构的协调算法

  L5 执行/监控层 (30%) — 最弱

  已实现:
  - PortfolioController: 多策略fallback + 时间预算分配
  - 独立组检测: BFS+union-find → footprint细化 → NAMO耦合合并
  - 部分计划缓存(bestPartialPlan)

  关键缺失:
  - BDI reasoning cycle: claudeopus47 §1.2.5描述的标准监控循环（感知→更新信念→检验意图→重规划）完全不存在
  - 在线重规划: Client.updateState 只应用成功的动作，不检测状态是否偏离计划预期
  - 滑动窗口执行: 当前是全量计划→全量执行。没有"规划N步→执行→观察→再规划"
  - Client 一旦plan完成就逐条发送，如果中途状态偏离（例如某条动作被server拒绝后的级联效应），没有重新规划的机制

  是运气重试而非算法修复
  ────────────────────────────────────────
  #: 8
  严重程度: 🟡 中等
  位置: Client.java:289-301
  问题描述: updateState 按顺序应用成功动作 (currentState.apply(actions[i], i))，但server语义是同步联合动作——应使用
    applyJointAction 而非逐agent应用 apply。这会导致中间状态与server实际状态不一致

  Bug #8 是最危险的：server的语义是"所有agent同时行动，基于执行前的状态判断成败"。但Client逐个应用成功动作，如果agent
  0和agent 1同时移动到相邻格且都成功，apply 链会产生一个实际不存在的中间状态。
