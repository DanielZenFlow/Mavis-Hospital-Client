A:引子：你这个问题里藏着关键洞察
你说"不能所有代码统一用 IW"——这一句话其实已经把事情看穿了。工程上之所以让人困扰的不是"用什么算法"，而是"在什么时候用什么算法"。这个"判断"本身才是工程的灵魂。如果你已经隐约意识到这一点，那你需要的就不是"再多学一个算法"，而是建立一套自上而下的诊断—决策心智模型，让"判断该用什么"成为一个可解释的过程，而不是凭感觉。
我会自上而下分七层带你过一遍这个心智模型。每层结尾会有一个停下来的考察点——你不用立刻回答，但请你在心里把答案想一遍再往下看，这样模型会沉下去。如果某个考察点你答不上来，记下来，下一轮我们专门展开那块。

第一层：从"选一个算法"到"工具箱思维"的根本转换
1.1 一个不太典型但很贴切的类比
医生看病的流程不是"用青霉素治所有病"，是"先诊断，再开药"。同一个症状（比如发烧）背后可能是十种不同的病，每种病配不同的治疗方案。诊断这一步看起来不"产出治疗"，但它其实决定了治疗的成败。
工程上的 dispatcher（分发器）就是这个"诊断"步骤。它不直接解决问题，但它决定了问题应该被送到哪个求解器。一个写得好的 dispatcher 比一个写得好的求解器更值钱——因为它让你已有的求解器都用对地方了。
1.2 这个转换对你意味着什么
你之前那个 portfolio 之所以"全是 PP"，本质是没有 dispatcher。所有问题都被一刀切送到 PP，PP 不行就 fallback 到 CBS，CBS 也不行就放弃。这不是 portfolio，是流水线。真正的 portfolio 是"先看问题长什么样，再决定送到哪条流水线"。
所以接下来的所有讨论，都建立在一个隐形的前提上：我们要建一个能描述"问题长什么样"的体系，再建一个把"问题样子"映射到"求解器"的映射表。前者叫问题分类学，后者叫调度策略。这两件事加起来才是"判断什么时候用什么"的完整答案。
1.3 考察点
如果让你现在用一句话概括"为什么 portfolio 没生效"，你会怎么说？我希望的答案大概是这样：因为我们没有真正在判断问题的形状，所有问题都被路由到了同一个分支。

第二层：把关卡的"形状"拆成可识别的维度
要建一个 dispatcher，第一步必须是把"关卡长什么样"用结构化语言描述出来。靠"我看一眼觉得这关挺难"是不行的，那个判断没法被代码执行。我们需要把"长什么样"翻译成几个可量化的维度。
2.1 维度一：能否拆成完全独立的子问题
这是最便宜也最重要的维度。如果你的关卡里有红色 agent 操作红色 box、绿色 agent 操作绿色 box，且红绿之间在空间上完全没有交叉（比如被一道墙隔开），那这个关卡其实是"两个小关卡的并排放置"，可以分两次独立求解、最后把动作序列合并。
这个识别不需要复杂算法。从颜色出发，先按颜色分组；每组里跑一遍 BFS 看空间可达范围；不同组的可达范围如果不重叠，就是独立的。代价小，收益大——状态空间从两组的乘积降到两组的相加。
2.1.1 这一维度上的诊断结果
判定为"完全独立"的关卡：根本不需要调度，直接拆成 N 个子问题各自求解。判定为"有耦合"的关卡：进入下一层维度判断。
2.2 维度二：对象之间的依赖密度
把所有"box 要进 goal"的子目标列出来，分析每对子目标之间的关系。如果 box A 当前的位置正好挡在 box B 通往它 goal 的必经路径上，那"先 B 后 A"就是不可行的——必须先 A 后 B。这种约束累积起来形成一张依赖图。
依赖密度低意味着这张图很稀疏：大多数对子目标之间没有约束，几乎可以任意顺序做。这种情况下 PP 几乎肯定够用。依赖密度高意味着这张图很密：每个 subgoal 都在等其他几个完成。这种情况就需要小心排序。
2.3 维度三：是否有循环依赖
这是最关键也最难的一类。当依赖图里出现"A 依赖 B、B 依赖 A"的环时，直接拓扑排序会失败——你找不到任何不违反依赖的次序。这就是你说的"破而后立"问题。
环的成因通常很具体：A 当前在 B 的 goal 上，B 当前在 A 的 goal 上。这种关卡占少数，但一旦出现，没有专门处理它就直接卡死。dispatcher 必须能识别这一类，并触发"破环"机制（这个机制我们第四层细讲）。
2.4 维度四：单个子任务本身的复杂度
即使你把任务切成"agent 0 把 box A 推到 (3,5)"这样的单子任务，这个子任务本身也有难易之分。如果 box A 现在在 (3,2)、要推到 (3,5)，而中间没有任何阻挡，这是简单子任务，A* 用 Manhattan 启发式毫秒级出结果。如果 box A 要穿过一个迷宫，启发式（直线距离）和实际路径差距很大，A* 会花大量时间在错误方向探索——这时候 IW(1) 或更聪明的启发式才显出价值。
2.5 考察点
让我给你一个具体场景：4 个 agent，2 红 2 蓝；地图是被一道墙隔成左右两个房间，红 agent 和红 box 都在左房间，蓝 agent 和蓝 box 都在右房间。你看到这个关卡，dispatcher 的第一步动作应该是什么？
希望你心里能答出来：先做维度一的判断——颜色不同 + 空间分离 → 直接拆成两个独立子问题，根本不进入后续维度的判断。如果你能答出这一步，说明工具箱思维已经入门了。

第三层：工具箱里到底有什么、各自擅长什么
把维度搞清楚之后，下一步是把工具列出来，每个工具配一句"它最适合什么形状"。这就是 dispatcher 的"映射表"。
3.1 单 agent 子任务的求解器
A* with Manhattan 启发式是基础款。它假设"目标在直线方向上，绕路代价不大"。当子任务路径基本是直的、障碍物不多时，它的速度和正确性都没有问题。它的弱点是当真实路径要绕大圈时，启发式严重低估，搜索会走错方向。
A* with FF heuristic（slides 03 那个 Fast-Forward 启发式）是进阶款。FF 的核心想法是"先在一个简化的世界里找一个粗略计划，用这个粗略计划的长度作为启发式"。这个粗略计划比 Manhattan 准确得多，能引导 A* 在复杂路径里少走弯路。代价是计算粗略计划本身要花时间，简单子任务上反而比 Manhattan 慢。
IW(1) 是另一种思路。它放弃 A* 的"启发式估算"，改用"新颖性剪枝"——只保留那些"第一次让某个变量取到某个值"的状态。在 hospital 域里这个"变量"通常就是 box 的位置，所以 IW(1) 的语义是"每个新位置我只探索一次，重复路径全剪掉"。它特别擅长"找路"型子任务：单 box 在地图上从 A 推到 B，地图复杂但不需要协调多个对象。
IW(2) 把新颖性扩展到二元组——"第一次让某两个变量同时取到某对值"。在 hospital 里它适用于"agent 和 box 联动"的场景：你要把 box A 推到目标，但 agent 必须先穿越复杂路径到 box 旁边，agent 位置和 box 位置都在变。IW(2) 的状态空间比 IW(1) 大，但对这类联动问题比 A* 高效得多。
SIW（serialized IW）是 IW 的"多任务串联"。当你有多个独立子目标要按序解决时，SIW 用 IW(1) 或 IW(2) 解第一个、保存状态、再解下一个，把多个子目标串成一个执行序列。在 hospital 域里 SIW 不是直接拿来用的——你的 SubgoalManager 已经在做"串联"，所以 SIW 的角色被你的 L3 替代了。
3.2 多 agent 协调层的求解器
PP 是简单可靠款。它给 agent 排个固定优先级，低优先级把高优先级的轨迹当移动障碍。它在依赖密度低的关卡里足够用。
Conflict-driven PP 是它的进化版。当 PP 失败时，分析具体冲突——"agent 0 在 t=15 想走 (3,4) 但 agent 1 在 t=15 也在 (3,4)"——生成两条约束分支（让 0 让、让 1 让），分别重跑。它有 CBS 的灵魂但实现比 CBS 简单。
Subgoal-level 回溯是更高一层的修复机制。当 conflict-driven PP 也修不好时，问题往往出在 subgoal 顺序——必须改变"先做谁"。这一层会把 PP 失败信号送回 SubgoalManager，加一条新约束（"X 必须在 Y 之前"）重新拓扑排序，然后整体再来一遍。
3.3 把工具和维度对应起来
这就是 dispatcher 的核心映射：
维度一判定独立 → 各自跑一个独立 single-agent pipeline，互不干扰。
维度二依赖密度低 → 任意顺序的 PP 即可。
维度二依赖密度高但无环 → 严格按依赖图拓扑排序，PP 跑每一步。
维度三有环 → 触发 escape subgoal 机制（第四层讲），破环后再用上面流程。
维度四子任务简单 → A* with Manhattan。
维度四子任务路径复杂 → A* with FF 或 IW(1)。
维度四 agent-box 联动复杂 → IW(2)。
3.4 考察点
如果让你给"关卡里 5 个 box 颜色相同、依赖图是一条线（A→B→C→D→E，无环）、每个 box 推到 goal 的路径都不超过 5 格"这个场景选工具，你会怎么组合？
希望你能答出：维度一不分离（同色），维度二中等依赖但无环，维度四子任务简单。所以方案是 SubgoalManager 拓扑排序按 A→B→C→D→E，每个 subgoal 用 A* with Manhattan 解决，协调层用 PP。在这个场景里，IW 不是首选——A* with Manhattan 已经够用，引入 IW 反而增加了复杂度而无收益。

第四层：破而后立——dependency cycle 怎么处理
这是你提到的核心难题，也是整个体系里最微妙的一环。我把它讲透。
4.1 cycle 的本质是什么
把"box A 要从当前位置 P_A 到目标位置 G_A"这个子目标看作一个节点。两个节点之间的边表示"必须先做谁"的约束。当 box A 当前位置 P_A 恰好等于 box B 的目标 G_B、box B 当前位置 P_B 恰好等于 box A 的目标 G_A 时，约束图里出现了 A→B（先把 A 推到 G_A，那 B 不能挡，但 B 在 P_B = G_A，所以 B 必须先动）和 B→A（同理 A 必须先动）的环。
这种环不是逻辑错误，是真实存在的物理依赖：你不可能同时把 A 和 B 都送到目标，必须有一个先离开它现在的位置（虽然它的现在位置就是别人的目标），让出空间，让对方完成，然后自己再回来。
4.2 escape subgoal：破环的关键概念
要破这个环，必须引入一个新的子目标——"临时把 X 推到一个不在任何活跃路径上的位置 P_temp"。这个子目标在原始关卡描述里不存在，是 dispatcher 自己合成出来的。它叫 escape subgoal、relocation subgoal、或者干脆就叫"临时挪开"。
引入它之后，依赖图从环变成了链：先把 A 临时挪到 P_temp（escape A），再把 B 推到 G_B，再把 A 从 P_temp 推到 G_A。环被破了，拓扑排序可行。
4.3 选 P_temp 不是简单的事
P_temp 必须满足几个条件：当前可达；A 能从 P_A 推到 P_temp；从 P_temp 出发 A 能推到 G_A；P_temp 不能挡住后续任何活跃子任务的路径。这是一个 constraint satisfaction 问题——候选位置可能就那么几个空地，每个候选都要验证四条约束。
工程上的做法不一定要最优——可以用一个启发式：在所有空地中，离 A 当前位置最近的那个、且不在 G_B 附近的，作为首选；如果首选行不通就换次选。这是"贪婪选择 + 失败回退"的标准套路。
4.4 这一步用什么工具
注意这里的子任务"把 A 推到 P_temp"是一个典型的 single-agent 简单子任务——它的目标位置不是预先指定的逻辑目标，而是一个临时的物理位置。这种子任务恰好是 IW(1) 的甜蜜点——你不在乎走最短路，只要能到就行；状态空间是单变量（A 的位置）；A* 的启发式可能不准（P_temp 是任意空地）但 IW(1) 不依赖启发式。
所以"破而后立"流程里，IW(1) 实际上扮演了非常自然的角色：它专门负责"把对象临时挪到某个空地"这种没有明确目标方向的子任务。这是 IW 真正发光的地方之一。
4.5 考察点
假设你看到一个关卡：两个红 box A 和 B，A 当前在 (3,3)、目标在 (5,5)；B 当前在 (5,5)、目标在 (3,3)。地图上还有几块空地比如 (2,2)、(4,4)、(6,6)。你的 dispatcher 应该如何决策？
希望你能答出大致流程：识别 cycle（A 和 B 互挡）→ 决定让 A 先挪（任意一个的选择都行，比如选当前位置 P_A 离空地更近的）→ 在候选空地中选 (2,2)（不在 G_B 附近、A 可达）作为 P_temp → 子目标序列变成 escape-A-to-(2,2) → push-B-to-(3,3) → push-A-to-(5,5) → 每个子目标分别用 IW(1) 或 A* 解决。

第五层：把整体工作流串起来——dispatcher 完整心智模型
到这里已经讲了所有零件，最后一步是把它们装成一台运转的机器。我用伪流程描述一遍，你读的时候在脑子里画框图。
5.1 接到一个关卡时 dispatcher 做什么
第一步是静态分析阶段。读入关卡，按颜色分组 agent 和 box，对每组跑一遍 BFS 计算空间可达范围，比较各组的可达范围有没有重叠。如果完全不重叠，立刻分裂成多个独立子问题，每个子问题进入下面的流程；如果重叠，整个保持为一个问题继续分析。
第二步是依赖图构建。列出所有 box-to-goal 的子目标，对每对子目标分析"是否相互阻挡"，构建依赖图。检测图中是否有环。
第三步是分支决策点。无环的情况下，对依赖图做拓扑排序，得到一个执行顺序。有环的情况下，识别每个环涉及的 box，为每个环引入 escape subgoal、把环转换成链。
第四步是子任务调度。对每个 subgoal，根据它的形状选择 single-agent solver——简单的用 A* + Manhattan，复杂路径用 A* + FF，临时挪移或单对象找路用 IW(1)，agent-box 联动用 IW(2)。
第五步是协调层运行。多 agent 的执行序列通过 PP 整合成 joint actions。当 PP 报告冲突时，先尝试 conflict-driven PP（在 action 层加约束）；这一步还修不好就回到 subgoal 层（加一条 ordering 约束重排）；这一步还修不好就回到分解层（重新评估哪些 subgoal 可以合并、哪些要拆得更细）。
第六步是输出 plan，向 server 发送 joint action 序列。
5.2 这个流程的关键是"失败信号自下而上传递"
注意上面流程里反复出现"修不好就退回上一层"。这才是这个体系的灵魂。每一层都有可能失败，每一层都有责任把"我搞不定"的具体原因传给上一层，而不是简单地报"无解"。
PP 失败时不是说"无解"，是说"agent 0 和 agent 1 在 t=15 撞了"——这个具体冲突信息让 conflict-driven PP 能加约束。conflict-driven PP 失败时是说"加了 N 个约束都没用，本质上是 agent 0 必须先于 agent 1 完成 task X"——这个信息让 subgoal 层能加 ordering 约束。subgoal 层失败时说"我已经试过所有 ordering 都不行"——这个信息让分解层重新切任务。
如果失败信号不够具体，自下而上的修复机制就退化成"盲目重试"。所以每一层 solver 的设计都要考虑"我失败时给上层留什么信息"。
5.3 IW 在整个体系中的位置回顾
到这里你应该看清楚 IW 的位置了：它是 single-agent solver level（也就是第二层）的一个工具，而且只在某些子任务形状下被选中。它不是"用来替代 A*"的，是"和 A* 互补"的。dispatcher 在每个 subgoal 上单独决定用哪个工具。
回到你最初的问题"高度依赖关卡的破而后立时怎么用 IW"——答案现在应该清楚了：IW 不直接处理"破而后立"这件事本身，那是分解层（cycle detection + escape subgoal 合成）的责任。但破而后立产生的"挪到任意空地"子任务，正好是 IW(1) 的甜蜜点。所以 IW 在这个体系里的位置是：上面有一层在做策略性决定（要不要破环、破谁、挪到哪），破完之后产生的具体子任务再交给 IW 高效求解。

第六层：留给你做的核心考察
我把上面所有内容浓缩成一个具体场景，请你尝试自己走一遍 dispatcher 的逻辑。
场景：关卡里有 3 个红色 agent，5 个红色 box A、B、C、D、E。A 当前在 (2,2)，目标在 (8,8)；B 当前在 (8,8)，目标在 (2,2)；C、D、E 各自的 path 不互相干扰、也不和 A、B 干扰。地图中部有一些空走廊。
我希望你心里能走完这个流程：
第一步，独立性检测——所有 agent 同色，要看空间是否分离。C、D、E 之间不干扰，A 和 B 之间互挡，所以可以分成两个子问题：{A, B} 一组、{C, D, E} 另一组（如果 C、D、E 也不和 A、B 在空间上重叠的话）。
第二步，对 {C, D, E} 这一组——依赖图无环、密度低，PP 直接出结果，每个 subgoal 用 A* + Manhattan 解。
第三步，对 {A, B} 这一组——依赖图是 A↔B 的环，触发 escape subgoal 机制。选一个空地 P_temp，把环破成 escape-A → push-B → push-A 的链。escape-A 用 IW(1)，push-B 和 push-A 看路径复杂度选 A* 或 IW(1)。
第四步，把两组的动作序列合并成 joint actions。

一句话总结
整个工程的本质，不是"我们要用什么算法"，而是"我们要建一套先看问题形状再选算法的 dispatcher，并且让每一层的失败信号都能够具体地、可操作地反馈给上一层"。IW 只是这个 dispatcher 上挂着的众多工具中的一个，它在某些子任务上无可替代，在另一些场景里反而是负担。判断"什么时候用 IW"的过程，就是把关卡的形状描述清楚、再查映射表的过程——这个过程能被代码化，就是 dispatcher。
