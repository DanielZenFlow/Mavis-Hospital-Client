一、用 SDE 思想完整解构这个工程
在讨论 portfolio、CBS、HTN 之前，我建议先把"工程上这件事是什么"讲清楚。你的迷茫来自一个常见错误：把课程上的知识点（PP、CBS、IW、HTN……）当成"功能模块"来选购，而不是当成"对某一层问题的不同解法"来理解。这样思考永远会陷入"我是不是该把这个也加进去"的焦虑。SDE 视角则相反：先分层，每一层只问"这一层在解什么问题"，再去问"用什么算法"。
1.1 先认清问题的本质
1.1.1 它不是教科书里的 MAPF
CBS、PP 这些算法的标准描述都假设一个非常干净的世界：每个 agent 是一个不占体积的点，从 A 走到 B；冲突只可能是"两个 agent 同一时刻占同一格"或"对穿"。在这种世界里，agent 之间唯一的相互作用是空间挤占，环境本身是静态的。
Hospital 域不满足这个假设。环境里有 box，box 占格子、能被推、能被拉、有自己的目标位置，且只能被同色 agent 操作。Agent 的"动作"也不再是简单地走一格——push 和 pull 把 agent 状态和 box 状态绑成了一个原子动作。这意味着冲突的种类被显著扩展：除了 agent-agent 冲突，还有 agent-box、box-box、push 方向被堵、pull 方向被堵、把 box 推进死胡同等等。
1.1.2 它在结构上更接近"多智能体 Sokoban"
如果你必须给这个问题贴一个学术标签，那不是 MAPF，而是 Cooperative Multi-Agent Sokoban with Pull。Sokoban 单独已经是 PSPACE-complete——它的"难"不是难在搜索深度，而是难在大量看似合理的中间状态其实是死局，需要规划器具备某种"前瞻性"才能避免把 box 推到角落。多 agent 让状态空间从单 agent 的指数级再叠一层指数。
理解这一点很重要，因为它直接决定了：纯粹"在联合状态空间里跑一个 A*"是不可能成功的。任何能跑赢的方案都必然在某种意义上把这个庞大问题切碎了再分别解。
1.1.3 这个本质决定了什么
第一，箱子才是 first-class 对象，agent 是手段。在多数关卡里只有 box 有 goal，agent 没有；即使 agent 有 goal，也通常要求"先把所有 box 安顿好，agent 自己找位置"。所以算法的最外层循环应当围绕"哪个 box 去哪个 goal、按什么次序"，而不是"哪个 agent 去哪里"。
第二，Pull 的存在从根本上改变了启发式。在没有 pull 的纯 Sokoban 里，箱子被推进角落基本就死了；有了 pull，理论上没有不可逆动作，但 pull 在 hospital 域里是有前置条件的（agent 要在箱子的反方向且那个方向是空的），并不是想拉就能拉。这意味着 deadlock detection 在这个域里仍然是有用的，只是判定标准要更精细。
第三，颜色约束是天然的任务划分线。红色 agent 永远不可能去碰绿色 box，因此任务分解的第一刀其实是免费的：按颜色把问题切成若干独立子问题。如果两个不同颜色的子问题在空间上完全分离，它们之间根本不需要协调；如果共享走廊，则只剩"通行权"这个最简单的协调问题。
1.2 SDE 视角下的工程分层
工程上看一个复杂系统，第一件事是分层，第二件事是把每一层的输入输出讲清楚——讲清楚的标志是：每一层都可以独立测试，每一层的实现可以被另一种实现替换而不影响别层。下面这五层不是我编的，它对应的就是课程里那些知识点各自所在的位置。
1.2.1 第一层：领域模型（Domain Layer）
这一层是 Slides 02（PDDL）的思想精髓：把"世界长什么样"和"想用什么算法解"彻底分开。这层里的代码应该完全没有 A*、没有启发式、没有优先级——只有 State 类、Action 类、Goal 判定、颜色约束、动作的 applicability 和 effect。
判断你这一层是否做得好的标准很简单：你能不能把这一层的 jar 包给另一个组的同学，他用任何搜索算法都能得到正确结果？如果你的 State 类里出现了 lastSearchHeuristic 这种字段，或者你的 Action 类里硬编码了 PP 的优先级逻辑，那就是越界，必须重构。
值得专门花精力的是 State 表示。多 agent 多 box 的状态如果用朴素表示（比如二维 char 数组）会让 hashCode/equals 慢到怀疑人生，搜索几十万个节点就会卡死。一个好的 State 用紧凑编码（agent 位置 + box 位置的有序数组），墙是 immutable 单例，hash 是增量计算的。这件事和搜索算法没关系，它属于领域层的职责。
1.2.2 第二层：单智能体求解器（Single-Agent Solver Layer）
这一层只回答一个问题：在一个被某种约束限制的世界里，单个 agent 怎么把一组（通常是一个）子目标完成。它的输入是"当前 state + subgoal + constraints（哪个格子在哪个时间步不能去）"，输出是"动作序列或无解"。
Slides 01 的 BFS/A*、Slides 03 的启发式、Slides 05 的 IW/SIW 全部归在这一层。它们之间的关系不是互斥的产品，而是同一接口的不同实现：当 subgoal 很简单（"把这个 box 推到隔壁"），IW(1) 几个毫秒就出结果；当 subgoal 复杂（"穿过一个迷宫"），需要带 FF-style 启发式的 A*。
很多客户端在这一层做得不好，会拖累整个系统。具体表现是：单个 box 的子任务都要花几秒，到 5 个 box 的关卡就直接超时。诊断起来不难：把这一层抽出来，单独跑几个 SAsimple 系列的关卡，看耗时。如果单 agent 一个简单关都要 1 秒以上，问题就在这层。
1.2.3 第三层：任务分解层（Task Decomposition Layer）
这层是 Slides 04（HTN）和 Slides 06（subgoal serialization）的核心思想：与其在巨大的联合状态空间里盲搜，不如把"完成整个关卡"拆成"一系列单 agent 子目标"，按依赖关系排序，逐个交给第二层去解。
为什么这层威力巨大？因为它把指数复杂度变成了多项式。原本你要在所有 agent 所有 box 的联合配置空间里搜索；分解之后，每次只需要搜索"一个 agent 做一件小事"的小空间，再把这些小解串起来。代价是：你必须保证子目标的次序是合理的——前一个子目标完成后留下的世界状态，能让下一个子目标 reachable。
子目标依赖图怎么建？典型的几种判定：box A 的 goal 在 box B 的某条可行路径上 → 必须先 B 后 A；agent 0 要 push 的 box 现在被 agent 1 的 box 挡着 → agent 1 必须先腾位置。这些判定可以用一些静态分析做，也可以失败后回溯（"这个顺序解不出来，试别的顺序"）。
如果你的 client "全是 PP"，最大的可能就是这一层是空的——你直接把每个 agent 当成"go to my goal"扔进协调层，从来没有"先做这个再做那个"的概念。这是性能问题的根本原因，不是 PP 本身的问题。
1.2.4 第四层：协调层（Coordination Layer）
第三层把任务切成单 agent 的子任务，但这些子任务在时空上仍可能撞车——agent 0 要走的路径上正好是 agent 1 还没解决的 box。这层的职责是：检测冲突、解决冲突。
PP 是这层最简单的实现：给 agent 排个固定优先级，低优先级把高优先级当移动障碍物（在第二层求解时把高优先级的轨迹作为时空约束传进去）。CBS 是更聪明的实现：所有 agent 先各自规划，碰撞了就生成一个分支约束（"agent 0 在 t=5 不能在 (3,4)"或"agent 1 在 t=5 不能在 (3,4)"），在两个分支里各自重新求解，整体上是个 best-first search of constraints。
PP 的失败模式很经典：环形依赖（A 等 B 让，B 等 A 让），这时 PP 没有任何修复机制，只能宣告失败。CBS 通过约束分裂可以避开这种失败，但代价是高级层的搜索分支可能爆炸。Slides 06 还提到一种思路：发生冲突时不在协调层补救，而是回到第三层调换子目标顺序——这是 subgoal-level 的回溯，往往比 CBS 更便宜。
1.2.5 第五层：执行与监控层（Execution Layer）
最高层。负责把规划好的 joint action 序列发给 server、读 server 返回的成功/失败、当现实和规划偏离时决定要不要重规划。Slides 08（BDI）的 reasoning cycle 描述的就是这一层：感知（server 反馈）→ 更新信念（当前 state）→ 检验意图（计划是否仍可行）→ 必要时重规划。
在 hospital 域里，由于 server 是确定性的、所有动作的 outcome 都被精确定义，理论上不需要重规划——你规划出的 plan 一定能执行成功。但实际工程里，你可能因为 timeout 或内存压力而 plan 一段、执行一段、再 plan 一段，这就需要监控层来管住"什么时候停下来重规划、什么时候继续"。
1.3 用这个分层重新看你当前的工程
1.3.1 "全是 PP" 揭示的是什么
PP 是协调层（第四层）的一种实现。如果你的整个系统的所有"智能"都集中在协调层，那意味着：
第一层（领域）大概率没问题，因为不做对的话根本跑不起来。
第二层（单 agent 求解）大概率是"基础版 A* + 基础启发式"，这层做不到极致，但能用。
第三层（任务分解）几乎不存在。每个 agent 直接把"goal"作为目标，扔给协调层去对齐。这才是性能的真正瓶颈，因为没有任务分解意味着每个 agent 在搜索时都要在自己的整个空间里折腾，且这个空间还嵌入了其他 agent 的轨迹作为时空约束，复杂度极高。
第四层（协调）只有 PP 一种实现。PP 失败时，整个系统失败。
第五层（执行）大概率只是个 server 通信的 wrapper。
1.3.2 正确的补救次序
工程直觉告诉你：哪一层最弱，先补哪一层；并且先补的层应该有最大的 ROI。
最该先补的是第三层。原因是：补好第三层，第二层的搜索空间会从"整个关卡"缩到"单步任务"，速度提升是数量级的；同时第四层的冲突频率会下降，因为子任务被切碎、agent 在世界里同时存在的"活跃区"变小了。也就是说，补第三层会自动让二、四层的弱点缓解。这就是高 ROI 的特征：动一处，三处受益。
第二层的优化（更好的启发式、IW）应该在第三层稳定之后做，因为只有当第三层把任务切到合适的粒度，第二层的算法选择才有意义。在没有任务分解时，再好的启发式都救不了你；任务一旦切碎到位，连最朴素的 BFS 都可能够用。
第四层的升级（PP → CBS / 回溯式 PP）应该排在最后。原因不是它不重要，而是只有当前面三层都做扎实了，你才会看清楚"哪些关卡确实需要更聪明的协调"——通常你会发现，认真做完任务分解之后，剩下需要协调的冲突量已经很小，PP 加少量回溯就能 cover 掉绝大多数。
二、关于 Portfolio：要不要做，以及什么时候做才有意义
2.1 Portfolio 在规划领域的真实含义
2.1.1 一个被反复误解的概念
"Portfolio planner"在 AI Planning 文献里有非常具体的含义：你有 N 个不同算法，它们对不同问题各有所长（一个对 Sokoban 强、一个对 Logistics 强、一个对 Blocksworld 强），你不知道下一个问题属于哪种类型，于是用一个 meta 层在 N 个算法之间做时间预算分配——比如轮转（每个算法跑 10 秒），或并行竞赛（同时跑，谁先出解谁赢），或基于关卡特征的预测分配。
这个概念预设的前提非常苛刻：N 个算法必须真的不同（否则就是一个算法多个副本），并且它们的优势区域必须真的互补（否则就是一个算法 + 几个废物）。
2.1.2 你说"portfolio 没生效，全是 PP"暴露了什么
这句话本身就揭示了你的"portfolio"违反了上面两个前提中的至少一个。要么是 N 个算法本质上还是一个算法，只是参数不同；要么是它们的优势区域被关卡分布完全覆盖在 PP 那个分支里——这两种情况都意味着没有 portfolio，只有伪装。
更准的诊断可能是：portfolio 框架是搭好了，但其他算法分支根本就没实现完整、或者关卡分类器有 bug，所有 case 都被路由到 PP。
2.2 你这个项目要不要做 portfolio
2.2.1 教学层面和工程层面是两个答案
教学层面，portfolio 对应的就是 Slides 06 那种"prioritized + 其他策略"的组合精神，是值得在视频里展示的工程素养。如果你能讲清楚"我们识别了三类关卡，每类用不同的算法"，这是有分量的。
工程层面，做 portfolio 的代价是巨大的。每多一个分支就意味着一整套独立的求解器要 debug、测试、调参；如果你的分支总数等于你的人数，你大概率每个分支都做不深。多数得分高的小组实际上做的不是真正的 portfolio，而是单一架构 + 局部技巧——比如统一用"任务分解 + IW + PP+回溯"，但在分解阶段对不同关卡用不同的分解策略。
2.2.2 我的建议
不要把 portfolio 作为目标，把"分层架构"作为目标。如果你认真做完了第三层（任务分解），你会自然得到一个"轻量级 portfolio"：在分解策略层面就有多种选项（按颜色分组、按依赖图分组、按空间区域分组），这些选项的选择本身就构成了一种 portfolio。这种 portfolio 比表面上跑多个 solver 的 portfolio 更有内涵，也更容易在视频里讲出技术含金量。
如果时间还很充裕（这种情况罕见），你再考虑真正的多 solver portfolio：比如一个分支用"任务分解 + IW"专攻 box-heavy 关卡，另一个分支用"CBS + Manhattan"专攻 corridor-heavy 关卡。但前提是你的分层框架已经稳定，加分支只是替换某一层的实现，而不是另起炉灶。
三、关于 CBS：在 Push-Pull Sokoban 下的适用性
3.1 CBS 的世界观和你的世界观
3.1.1 CBS 假设的世界
CBS 的设计假设是 vanilla MAPF：agent 是无体积的点，环境是静态的，agent 的动作只有"移动到邻格或停留"，冲突类型有限（vertex conflict 和 edge/swap conflict），单 agent 求解器（low level）是 space-time A*——状态维度是"位置 + 时间"，输入是"目标 + 一组在某时刻禁止的位置"，输出是带时间标签的路径。
3.1.2 这些假设在 hospital 域里几乎全部失效
Agent 不是无体积——它本身要占格子。环境不是静态——box 的位置在动。动作不只有移动——还有 push 和 pull，它们同时改变 agent 和 box 的状态。冲突类型远不止 vertex/swap——agent 要 push 一个 box 时，box 的目标格被另一个 agent 占住、或被另一个 box 占住、或被刚要走来的另一个 agent 计划占住，全是新冲突类型。Low level 也变了——不再是 space-time A* on grid，而是 space-time A* on (agent position × box positions)，状态维度爆炸。
把 CBS 完整移植到 hospital 域，理论上可行（学术圈有 MAPF-with-payload、push-and-rotate 等扩展），但实现量是博士论文级别。对于一个本科课程项目，性价比极低。
3.2 CBS 思想可以借鉴，但整体不要移植
3.2.1 真正可借鉴的是约束生成这个机制
CBS 最有价值的内核是"碰撞→生成约束→分支重规划"的循环，而不是它具体用什么 low-level solver。这个内核可以套在你的 PP 之上：当 PP 因为冲突失败时，不要简单宣告失败，而是分析冲突的具体内容（"agent 0 在 t=5 想推 box A 进 (3,4)，但 agent 1 在 t=5 也在 (3,4)"），生成两个约束分支（"约束 agent 0 别这么干"和"约束 agent 1 别这么干"），分别重跑 PP 看哪个能成。这就是"PP with backtracking"或者叫"conflict-driven PP"，它有 CBS 的精神但没有 CBS 的实现复杂度。
3.2.2 一个更适合你这个域的思路：在子目标层做 CBS-lite
回到第三层的任务分解。如果两个 agent 的子目标序列在执行时撞了车，与其在 action 层添加约束，不如在 subgoal 层添加约束："agent 0 必须先完成 subgoal X，再完成 subgoal Y"。这种约束的搜索空间比 action-level 约束小得多——subgoal 总共可能就十几个，action 可能上千个。
这其实是 Slides 06 那一行字"Subgoal Serialization 用拓扑排序或依赖图，决定哪个目标必须先被满足"的工程化展开。它本质上是一个把 CBS 的二级搜索思想搬到子目标层的策略，比直接做 CBS 在 hospital 域里实现成本低一两个数量级，且在多数关卡上效果不差。
四、所以"最优解"大致长什么样
如果让我画一个理想的 hospital client 架构，它会是这样的：领域层提供高效的 State/Action/Goal 抽象，hashCode 和 successor 函数都被仔细优化过；单 agent 求解层有两个或三个可互换的实现（朴素 A*、A* with FF-heuristic、IW(1) 或 SIW），由分解层根据子任务类型选择；分解层是整个系统的大脑，它分析关卡的颜色分布、box 依赖关系、空间结构，生成一个带依赖关系的 subgoal 图；协调层默认用 PP，遇到冲突先在 subgoal 层重排（最便宜的修复），再不行才在 action 层加约束（CBS-lite）；执行层负责吐 action 给 server 并监控异常。
这个架构对应的课程知识点是这样的：领域层用 PDDL 思想（Slides 02）；单 agent 层用 Slides 01 的搜索 + Slides 03 的启发式 + Slides 05 的 IW/SIW；分解层用 Slides 04 的 HTN 思想 + Slides 06 的 subgoal serialization；协调层用 Slides 06 的 PP + Slides 07 的 CBS 思想（不是完整算法）；执行层用 Slides 08 的 BDI cycle。每一层都在课程的知识地图里有位置，没有哪个知识点是为了凑数硬塞进来的。
我刻意没有把 CBS 完整算法和真正的 portfolio 放进这个理想架构。原因是它们对这个项目的边际收益太低：CBS 的实现成本不能换来明显更高的解题率（PP+回溯+任务分解已经能覆盖绝大多数关卡），portfolio 在没有真正多样的求解器之前就是空架子。把这两件事砍掉，你能省出大量时间把分层架构和任务分解做扎实——这才是评分老师在视频里真正想看到的"算法 ideas 的 novelty 和 quality"。
