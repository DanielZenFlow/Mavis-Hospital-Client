一、MAPF-LNS 论文方法回顾
1.1 核心问题与定位
论文解决的问题是：现有 MAPF 算法要么最优但不可扩展（CBS），要么可扩展但质量差（PP、PPS）。MAPF-LNS 要做的是第三条路——anytime 算法：

快速找到一个初始解（哪怕很差）→ 在剩余时间内持续改进

论文 Figure 1 画得很清楚——MAPF-LNS 占据了「Near-Optimal + Large Scale」的位置，是唯一同时兼顾质量和规模的算法。

1.2 算法骨架
MAPF-LNS(problem, time_limit):
  P ← InitialSolver(problem)           // 用 PP/EECBS/PPS 快速拿到初始解
  while time_remaining > 0:
      A_s ← SELECT_NEIGHBORHOOD(P, N)  // 选一组 agent（大小为 N）
      P_s⁻ ← {p ∈ P | agent(p) ∈ A_s} // 取出它们的旧路径
      P_s⁺ ← REPLAN(A_s, P \ P_s⁻)    // 把其余路径视为移动障碍，重规划
      if sum_cost(P_s⁺) < sum_cost(P_s⁻):
          P ← (P \ P_s⁻) ∪ P_s⁺       // 接受改进
  return P

关键点：每次只动一小撮 agent（论文用 N=4~16），其余保持不变。 这就是「Large Neighborhood Search」的精髓——每次搜索的空间是 N 个 agent 的联合空间，而不是全部 agent 的联合空间。

1.3 三种邻域选择（Destroy 启发式）
这是论文的核心贡献。选哪些 agent 来重规划？

Agent-Based（Algorithm 1）：选 delay 最大的 agent a_k（即路径最偏离最短路的那个），沿它的路径做 random walk，把沿途碰撞的 agent 加入集合。直觉：路径最差的 agent 最值得改进，而跟它冲突的 agent 一起重规划才有可能改进。

Map-Based（Algorithm 2）：找地图上的交叉点（degree ≥ 3），BFS 收集经过该交叉点的 agent。直觉：交叉点是瓶颈，经过同一瓶颈的 agent 一起重规划，可能找到更好的通过顺序。

Random：随机选 N 个。直觉：简单但在拥挤场景下出奇有效（因为拥挤时随便选几个 agent 大概率就是互相影响的）。

1.4 ALNS — 自适应选择
三种启发式通过 roulette wheel selection 竞争，表现好的权重上升，表现差的下降。γ=0.01 控制反应速度。这让算法自动适应不同场景。

1.5 Replan（Repair）步骤
论文的 repair 方法是：把剩余 agent 的路径视为时空障碍，然后用标准 MAPF 算法（PP 或 CBS）为选中的 agent 子集重新规划。论文实验表明 PP 做 repair 效果最好（因为快，一次迭代的时间短，能做更多次迭代）。

1.6 实验结论
初始解质量不太重要（PP、EECBS、PPS 的初始解不同，但 LNS 迭代后趋同）
PP 做 repair 最好（比 CBS 快，能做更多迭代）
ALNS 总体最优（三种启发式互补）
60s 内 sum of delays 最多降低 36 倍
在 den520d 900 agent 级别仍然有效

三、我认为 VS Code Claude 的判断是部分正确但过于保守
3.1 它说对了什么
适配成本确实存在。 论文假设 agent 只能 Move/Wait，解的表示是纯位置序列。你的项目中 agent 要 Push/Pull box，解是 Action[][]，agent 和 box 耦合。这意味着：

移除一个 agent 的「路径」同时要移除它操纵的 box 的运动轨迹
Repair 时不仅要避免 agent 冲突，还要避免 box 冲突
Box 被推到 goal 后可能被其他 agent 的 repair 破坏
这些都是真实的工程挑战。

3.2 它哪里判断错了
它把「适配有难度」等同于「不适合」，这是逻辑跳跃。

让我用你文档中的实际数据来论证 MAPF-LNS 的适用性：

3.3 Push/Pull 的适配方案其实并不复杂
VS Code Claude 把 Push/Pull 适配描述得过于困难了。实际上：

关键洞察：在 Hospital Domain 中，agent 和它当前操纵的 box 可以视为一个「超级 agent」。

标准 MAPF agent:  位置 = (row, col)
Hospital agent:   位置 = (agent_row, agent_col, box_row, box_col, box_id)
                  或者当 agent 没在操纵 box 时 = (agent_row, agent_col, ∅)

在 LNS 框架中：

Destroy：选一组 agent，移除它们的路径 以及 它们操纵的 box 的运动轨迹 → box 回到该 agent 接触它之前的位置
Repair：用 BSP 为这组 agent 重新规划（BSP 天然处理 Push/Pull）
Accept：比较 cost（已完成的目标数 + 总步数）
你的 BSP 已经支持 Push/Pull，ReservationTable 已经存在。BSP 就是论文中「低层规划器」的 Push/Pull 版本。
